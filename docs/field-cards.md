# 字段卡（Field Cards）

> 建立：2026-10-09 · 起因：思维朋友抽查发现「字段没有单一事实来源」
> 执行：`scripts/field-guard.py`（能自动修的修掉、不能修的报出来、都留痕）
> 报告输出：`data/_field-report.md`

**为什么要有这个文件**：字段卡不是为了规范，是为了**让「零」和「异常」能被发现**。
`boards` 里冒出 `regulatory` 不会报错，它只会安静地出现在一个筛选不到的地方 —— **和「真的没有」长得一模一样**。

---

## boards

| 项 | 内容 |
|---|---|
| **定义** | 这条情报属于站点的哪个**板块** |
| **取值范围** | `reg` / `product` / `insurer` / `tech` / `market` / `family` —— **封闭枚举，6 个** |
| **谁写入** | 采集流程（唯一写入方） |
| **谁读取** | 前端板块筛选（首页 6 张卡）、主题雷达 |
| **兜底** | 出现枚举外的值 → `field-guard.py` 自动归位 + 记 warning，**不静默通过** |

**归位规则**（非正式取值不是"错误"，是**放错字段**）：

| 原值 | 去向 | 依据 |
|---|---|---|
| `firm` / `company` / `carrier` | → `insurer`（板块） | 同义 |
| `regulatory` / `compliance` / `supervision` | → `reg`（板块） | 同义 |
| `macro` / `economy` / `capital` | → `market`（板块） | 同义 |
| `ai` / `insurtech` / `digital` / `fintech` | → `tech`（板块） | 同义 |
| `product-design` / `channel` | → `product`（板块） | 同义 |
| `ils` / `cat` / `marine` / `offshore` / `cross` / `intl` / `health` | → **`themes`（主题）** | **它们是主题，不是板块**——放错了字段 |

> 最后一行是这次的关键区分：`ils`（保险相连证券）、`cat`（巨灾）、`marine`（海事）不是"板块"，是**主题**。板块管导航，主题管检索。

## verifyStatus

| 项 | 内容 |
|---|---|
| **定义** | 这条情报的来源是否已**回到原文**核对过 |
| **取值范围** | `verified` / `pending` —— 封闭枚举 |
| **谁写入** | 采集流程 |
| **谁读取** | 前端徽章（「已核原文 / 待复核」） |
| **兜底** | 缺失 → 记警告（默认不得为 `verified`） |

**成文规则（原先只存在于实现里，现在写下来）**：
- **official / insurer 源**（监管原文、保司官网）→ URL 即原文，**抓取即核** → `verified`
- **media / pro 源**（媒体报道、第三方解读）→ 是**转述**不是原文 → 默认 `pending`，需回到事件源头核
- **超时**：`pending` 超过 **90 天**未复核 → `field-guard.py` 报出（当前 7 条，最久 631 天）

> ⚠️ 未解决：按此规则，449 条 media 里应当大部分是 `pending`，但实测只有 121 条。**差额来自早期入库的判定不一致**——这条待查。

## sourceKey

| 项 | 内容 |
|---|---|
| **定义** | 情报的**内容主体机构**（不是抓取渠道域名） |
| **取值范围** | 开放，但**必须从 `source.name` 稳定派生** |
| **谁写入** | `structure-sources.py`（从 name 派生）／采集流程 |
| **谁读取** | 信源统计、`intelligence.sourceTiers`、层级筛选 |
| **兜底** | `name` 解析不出 → 保留原 key，不臆造新值 |

**为什么定「机构」不定「渠道」**：读者关心"这是谁说的/关于谁的"，不关心"从哪个网站抓的"；渠道信息在 `originalUrl` 里，随时可查；而"渠道质量"这层**已由 `sourceTier` 承担**（official / media / pro / insurer / research / broker）。

## source（对象）

| 项 | 内容 |
|---|---|
| **定义** | 来源的**结构化描述**（取代原先一整串自由文本） |
| **取值** | `name`（机构名，规范）· `date`（来源标注日期）· `note`（溯源备注）· `lang` · `sc` / `tc`（显示用，**保留原文不动**） |
| **谁写入** | `structure-sources.py` |
| **谁读取** | 前端来源行；`sourceKey` 的派生源 |
| **兜底** | 解析拿不准 → **整体留在 `name`**，`date`/`note` 留空，**不猜** |

> 已回滚过一次教训：曾对 `sc` 做「去日期」文本清污（346 条），造成同源两种格式并存，且删掉了有溯源价值的备注（「转载《明报》…」「[EN原文，待核原文]」）。**根因不是"文本里有日期"，是"没有结构"。删字只是把问题藏起来。**

## clusterCount

| 项 | 内容 |
|---|---|
| **定义** | 同题聚合：有几条源在报道**同一件事** |
| **取值范围** | 整数 ≥ 1 |
| **谁写入** | **目前无人**（设计态） |
| **谁读取** | **前端 0 处引用**（但 i18n 有「源同题」文案） |
| **兜底** | 未聚合时默认 `1` |

**状态：待接，不是废弃。** 头部两源（insuranceasia 201 + insurancebusinessmag 151）常报道同一事件，用户会看到重复内容——这个字段正是为此设计的。

## summary

| 项 | 内容 |
|---|---|
| **定义** | **摘要**（当前实测 43–966 字，装了两样东西） |
| **取值范围** | 建议拆为 `summaryShort`（导语 ≤120 字）/ `summary`（完整） |
| **谁写入** | 采集流程 |
| **谁读取** | 列表（宜用短）/ 详情（宜用全） |
| **兜底** | 短版缺失 → 从长版截取 |
