# source 字段结构化方案（待拍板）

> 提出：2026-10-08 · 状态：**待 Leon 拍板** · 属「分类体系改动」，按铁律先出方案再动手

## 一、问题

`source.sc` 是**入库时自由生成的文本**，实测 **833 个唯一值**，格式无约束，混装了三类信息：

| 实际内容 | 例子 |
|---|---|
| 机构/媒体名 | `Insurance Asia`、`香港金融管理局 HKMA` |
| 日期 | `Artemis 2026-10-06`、`香港金融管理局新闻稿（2026-09-30 16:30）` |
| 溯源备注 | `大纪元时报（香港）转载《明报》2026-10-03 16:18 报道`、`[EN原文，待核原文]`、`据 FSS 数据、首尔经济日报与 SBS 报道` |

`sourceKey` 从 `source.sc` 派生 → 派生规则不稳定 → **同一媒体分叉成多个 key**、**同一 key 跨多个域名**（`ia` 121 条/22 域、`nfra` 41/17）。

## 二、已做（低风险，已上线）

- **合并明确同义的 key** 24 条：`insurancebusiness → insurancebusinessmag`、`InsuranceAsia → insuranceasia`、`chinalife/chinlife → china-life`、`ctf-life → ctflife`、`axa-hk → axa`、`prudential-hk → prudential`、`hkma_press → hkma`、`港交所 HKEX → hkex`、`mof-sta → mof`
- 工具：`scripts/cleanup-sources.py`

## 三、已回滚（重要教训）

曾对 `source.sc` 做「去日期/去标记」文本清污（346 条），**已回滚**，原因：

1. **造成新的不一致**——被清的 `Artemis 2026-10-06 報道` → `Artemis`，未清的 `Artemis 2026-10-05` 原样保留；同类来源两种格式并存。
2. **删掉了有溯源价值的信息**——`大纪元时报（香港）转载《明报》2026-10-03 16:18 报道`、`[EN原文，待核原文]`、`据 FSS 数据、首尔经济日报与 SBS 报道` 都是**多源交叉与复核状态**，对「每条可溯源」这个定位是有用的。
3. **根因没解决**——问题不是"文本里有日期"，是"**没有结构**"。删字只是把问题藏起来。

## 四、方案（三选一）

### 方案 A：拆三字段（推荐）

```json
"source": {
  "name": "Insurance Asia",                    // 规范机构/媒体名，用于统计与显示
  "date": "2026-10-06",                        // 来源标注日期（可空）
  "note": "据 FSS 数据、首尔经济日报与 SBS 报道", // 溯源备注（可空）
  "lang": "en",
  "sc": "Insurance Asia（2026-10-06）",         // 显示字段（由前三者合成，前端不改）
  "tc": "…"
}
```
- **优点**：`sourceKey` 可由 `name` 稳定派生（统计不再错乱）；日期与备注不丢且可单独使用
- **成本**：一次性解析 1206 条（规则解析 + 抽查），rebuild 后上线
- **风险**：解析歧义（如"金管局新闻稿（2026-09-30 16:30）"里的括号是日期还是标题一部分）→ 解析不出就整体留在 `name`，不猜

### 方案 B：只规范 `name`，日期/备注合成到 `note`
比 A 轻，但显示会变（日期从来源里消失，改由 `note` 承载）。

### 方案 C：不动结构，只约束「新入库」
在 collector 侧加写入模板（`name（YYYY-MM-DD）[备注]`），老数据不动。
- **优点**：零风险
- **缺点**：存量 833 个唯一值继续错乱，统计照旧失真

## 五、需要你拍板的

3. 日期在「来源」里是否保留显示？（站点已有 `publishedAt` 字段单独显示时间）
